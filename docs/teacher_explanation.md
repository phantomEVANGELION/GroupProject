# 需求变更说明

老师您好。针对您提出的四条修改方向，我们已经逐条进行分析与设计，现将实施方案向您汇报。

## 一、关于系统定位的转变

您提出的"从咨询到操作"这一方向，我们理解为核心在于：原系统以信息输出为终点，用户获得分析报告后仍需自行执行后续动作；新系统应以任务生成为起点，将分析能力嵌入操作流程之中，使用户的每一个操作意图都能直接触发对应的执行链路。

基于这一理解，我们保留原有分析能力的完整性与首页、导航栏等既有结构，在其上构建一个 Agent 工作台。工作台以"操作面板"替代"报告页面"，用户选择目标（分析 / 客服 / 营销 / 咨询）后，系统直接进入对应的工作界面，而非停留在结果展示页。原有功能不受影响，新增部分与原有部分可平滑切换。

## 二、关于 AI 客服功能

我们设计了一个完整的客服工作台模块，核心逻辑如下：

- 系统通过数据面板呈现店铺经营概况（今日收入、订单量、待处理消息数），为商家提供决策参照
- 顾客咨询以队列形式呈现，商家可直观查看当前所有待处理会话的概览信息
- 商家进入具体会话后，AI 基于店铺产品知识库自动生成回复草稿，商家确认或修改后发出
- 所有客服回复均经人工确认环节，避免 AI 直接对外输出可能带来的风险

该模块的业务逻辑完整，数据层预留了接入 Amazon SP-API 与 Shopify Admin API 的接口定义，当前演示阶段使用模拟数据运转。如需对接真实店铺数据，只需替换数据层函数实现，上游逻辑无需改动。

## 三、关于 AI 自动发帖

我们设计了一个面向社交媒体平台的营销内容生成与发布模块：

- 系统自动读取店铺产品信息，经 LLM 推理生成适配 X（Twitter）、Facebook、Instagram 三种平台调性的推广内容
- 生成结果以预览形式呈现，商家可在发布前进行编辑调整
- 商家选择目标平台后，系统执行发布操作，所有发布行为记录至本地操作日志
- 发布模块采用开关式设计，当前开关置于"模拟"档位，调用各平台 API 的实现代码已编写完毕，接入真实平台时仅需翻转开关并配置密钥

三个平台的 API 接入代码均已编写，当前演示阶段仅在本地的操作日志中记录发布行为，不向外部发送请求。

## 四、关于 AI 聊天功能

我们设计了一个基于 deepseek-chat 模型的对话模块，嵌入工作台作为常驻交互入口：

- 对话模型以店铺产品知识库作为系统提示词的上下文来源，使回答具备针对性和可操作性
- 支持多轮对话，历史消息由前端维护，每次请求携带最近若干轮上下文
- 不维护服务端会话状态，降低系统复杂度，同时便于后续接入完整的对话管理模块

该模块对外表现为一个即时对话窗口，用户可在此完成策略咨询、问题诊断、方案探讨等开放式交互。

## 五、各模块之间的协同关系

四个模块共享同一套店铺知识库（store_kb），该知识库通过 RAG 机制为所有模块提供一致的上下文信息。商家只需上传一份店铺配置文件（含产品目录、公司信息、资金概况、账号信息等），即可在四个模块中获得相互关联、互为参照的服务体验。这一设计避免了信息孤岛，也减少了商家的重复配置成本。
